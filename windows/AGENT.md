# AGENT.md — Notio for Windows

> **About this document.** Mirrors the role of `../docs/AGENT_EN.md` on the Android side: the working log and the
> numbered Decision Log for this sibling project. Everything below is planning; nothing here has been built. See
> `../docs/AGENT_EN.md` §2.1 for the cross-platform map (this project's place in it) and §1.1 rule 13 for the process
> that keeps this file from going stale as the Android app grows (its §5 table lists every Android feature to carry over).

## 1. Rules

This project inherits the Android app's process rules (`../docs/AGENT_EN.md` §1.1, §1.1.1, §1.2, §1.3) until its own
`RULES.md` exists to state anything Windows-specific differently. In particular: ambiguity gets one question at a time
with a recommended option, decisions go in the Decision Log below before implementation, and this file is git-ignored
(`.gitignore`, `/Notio-Windows/`) until the user decides to make it real, tracked work.

**Cloud services are on pause (Android `docs/AGENT_EN.md` §1.1 rule 14, user, 2026-09-24):** no Google Drive / Yandex Disk / other cloud sign-in, sync or backups in this project either, until the user lifts the pause.

**Parity rule revised (user, 2026-09-27: "new functions come from the Android version, desktop ones are marked desktop-only, and then they are synced with Notio Linux; if I explicitly ask to sync some function to Android, then add it to the Android version's TODO list; otherwise only to the Linux version").** This supersedes the directions of the rule below: (1) **Android -> desktop:** every user-facing function added, changed or improved on Android goes to Windows §5 and Linux §5 as before. (2) **Desktop-only functions** (window, tray, keyboard, single instance, installers …) are marked **DESKTOP-ONLY** in the Decision Log of the project that builds them and go **only to the other desktop project** (Windows -> Linux §5.1, Linux -> Windows §5.1); they are **not** sent to Android §2.2. (3) **To Android** a desktop function goes only when the user explicitly asks for it: then it is added to `D:\Notio-Android\docs\TODO_IDEAS_RU.md` (and its §2.2 row), nothing else.

**Three-way feature parity (the main rule; user, 2026-09-24: "the main rule, in our project and in the Android one: every change of functions — adding, improving — is recorded in the root project and in the linked one, so that the linked project is brought up to the current state; if we build functions in the Windows version, the Android project must know about it and get the same functionality, and the other way round"; "the same for the Linux project, the Notio-Linux folder: a link between all three").** The three Notio projects — Android (`D:\Notio-Android`), Windows
(`D:\Notio-Windows`), Linux (`D:\Notio-Linux`) — are one product. Whenever a user-facing function is **added, changed or improved** in any of them,
the **same working step** records it in the Decision Log of that project **and** adds a row to the incoming table of **each
of the two other projects**:
- into Android: `D:\Notio-Android\docs\AGENT_EN.md` §2.2 "Features to take over from the desktop apps";
- into Windows: `D:\Notio-Windows\AGENT.md` §5 (from Android) or §5.1 (from Linux);
- into Linux: `D:\Notio-Linux\AGENT.md` §5 (from Android) or §5.1 (from Windows).
A row holds the source project and decision ID, one line of what it is, the source version, and `PLANNED`; it stays `PLANNED`
until the receiving project ships it (`DONE <version>`), adapts it (`ADAPTED: <how>`) or the user rules it platform-only
(`NOT CARRIED OVER: <why>`). Bug fixes that only restore decided behaviour and internal refactors are not rows; platform
mechanics (permissions, installers, tray) are translated, not copied. At the start of a working step the agent reads this
project's incoming tables for `PLANNED` rows that touch the task, and at the end checks that every function it added reached
the other two. This project's own new functions go to Android §2.2 and Linux §5.1; incoming rows are §5 (Android) and §5.1 (Linux) below. (D11)

**Android rule 20 (D259): clean up after every build step, nothing left on drive C** (user, 2026-09-27); also the temp / tmp
files and folders a build leaves inside the project are removed after it (Android: `tools/clean_after_build.sh`). The test tasks must set
`java.io.tmpdir` to a folder inside the project's `build/` and remove it after the run (as Android's `app/build.gradle.kts` does);
packaging scratch goes into `build/` too; anything a step still makes outside the project is removed in the same step — only what the
step made. **Confirmed by the user again 2026-09-28 ("do not forget to clean the rubbish after the builds, all the temp and tmp folders and files — write it into your rule"): after every build `bash tools/clean_after_build.sh` runs, and after it no `tmp` / `temp` folder is left in the project (`build/tmp` of every module, the packaging scratch `desktopApp/build/compose/tmp`, the self-test folders) and no file of this project in `%TEMP%` (tests, sync, JNA, SQLite, the Kotlin daemon logs and its `kotlin-compiler-in-*otioindows*` markers); what belongs to other projects or to Windows is not touched.** Applied in 0.9.1 (`tools/clean_after_build.sh`, the test tasks' `java.io.tmpdir`).

**Android rule 19 (D258): this project keeps its whole build stack in `DEV_SETUP.md`** (what to install, versions, commands, what does not travel through git), updated with every change of the stack and read first on a new computer.

**Reliable and stable, fast, not greedy (user, 2026-09-27: "the rule: reliable-stable, performant, not greedy, ok? be sure to write it down, and then go through the code once you finish all the points of the implementation from Android").** Every piece of code of this project is written and checked for (1) reliability and stability: no crash paths (a failure is a message and a log line), no endless loops, nothing that blocks the window's thread (files, network, mDNS, the database off it), data never left half-written; (2) performance: no heavy work per frame or per row, lists worked out once per change, pictures decoded bounded and cached; (3) economy: nothing polling or awake without need, no timers while idle, native memory (Skia images, surfaces) and streams closed at once. **After the last block of §6.1 a whole-code pass is made against this rule** (§6.1 row 19), its findings fixed and written in the Decision Log.

**Android rules 16 - 18 apply here too (user, 2026-09-27; D233, D240, D243):** (16) a new batch of requests is first written into the
plan (Decision Log with open questions, the progress list, the other two projects' tables), the user chooses the order, the docs are
updated in the same step, and every significant finished piece is committed without being asked (no AI attribution); (17) every new
version is built in all the forms the user tests (on Android: the debug and the release APK; here: the installer / package and the
portable build of this platform, once they exist); (18) every code check covers stability / reliability (no crash paths, no endless
loops, no blocking of the UI thread), economy (nothing polling or awake without need) and performance / resources (no heavy work per
frame, bounded images, streams closed).

## 2. Product description

The same product as `../docs/AGENT_EN.md` §2 (all eleven note kinds, folders, tags, search, trash, reminders, app lock,
themes, ten languages, export/import, undo / redo, database encryption), native to Windows, plus the sync-node role described in §2.1 of that document.
Not restated here in full — that section is the authoritative reference; this file only tracks what is specific to
the Windows build.

## 3. Glossary

Same terms as `../docs/AGENT_EN.md` §3, plus:

| Term | Definition |
| --- | --- |
| **Sync node** | A Notio-Windows (or Notio-Linux) instance with its sync role turned on: listens for paired clients on the local network, holds its own full copy of the data. See `../docs/AGENT_EN.md` §2.1. |
| **Pairing** | The one-time, code-based handshake that lets a phone and a sync node trust each other from then on. See `../docs/AGENT_EN.md` §2.1. |
