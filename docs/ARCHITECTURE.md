# Общая архитектура Notio

## Назначение

Android и Windows — клиенты одного офлайн-продукта. Общее поведение и смысл данных должны совпадать; взаимодействие с ОС и адаптация интерфейса остаются платформенными.

## Что есть в эталонах

| Область | Notio-Android | Notio-Windows |
| --- | --- | --- |
| Gradle-модули | Один Android-модуль `:app` | Kotlin Multiplatform `:shared` и Compose Desktop `:desktopApp` |
| UI | Android Jetpack Compose | Compose Multiplatform для JVM/Desktop |
| Локальные данные | Android-хранилище, Room, Android API | Windows/JVM хранилище и системные адаптеры |
| Общая база исходников | Логика сейчас размещена в Android-приложении | `:shared` содержит переносимую логику Windows; большая часть её исходников пока расположена в `jvmMain`, а `commonMain` невелик |
| Переводы | Android `res/values*` | Есть Gradle-задача `syncAndroidStrings`, копирующая Android-строки в ресурсы desktop-клиента |

## Как устроен общий код в FitEasy

FitEasy применяет прямое подключение общего каталога исходников: Gradle Android-модуля добавляет `../shared/src` к своим Kotlin-исходникам, а Windows `desktopApp` добавляет тот же каталог в `jvmMain`. В `settings.gradle.kts` подключены только `:app` и `:desktopApp`; каталога `shared` как отдельного Gradle/Kotlin Multiplatform-модуля нет.

Это значит, что одинаковые Kotlin-файлы компилируются в обе программы. Там действительно есть общие модели, вычисления и Compose-компоненты. При этом каталог не является переносимым `commonMain`: среди зависимостей исходников есть Java API (`java.time`, `java.security`, `javax.crypto`) и Compose UI. Такой подход удобен, когда обе целевые платформы поддерживают эти API и согласованные версии библиотек; он сам по себе не гарантирует переносимость на другие Kotlin-платформы.

Для Notio FitEasy — хороший образец того, как начать с одного источника файлов и одной поставки Gradle. Архитектурно более ясной целью для Notio остаётся постепенно отделить действительно платформенно-независимое ядро от Android/JVM адаптеров. Не нужно механически копировать структуру FitEasy или предполагать, что каталог с именем `shared` уже равен KMP `commonMain`.

Модуль `:shared` из Notio-Windows нельзя считать уже готовой общей библиотекой Android/Windows. При объединении нужно разбирать исходники по слоям и переносить в общие source sets только код, который действительно не зависит от Android или JVM API.

## FitEasy как образец структуры

Общий стиль сборки берём из FitEasy: один Gradle root, модули Android `:app` и Windows `:desktopApp`, один источник версии и каталог Kotlin-исходников, который оба приложения подключают напрямую. Отдельная Kotlin Multiplatform библиотека не обязательна для первого этапа.

В Notio-Windows уже есть модуль `:shared`, но его `commonMain` пока содержит минимум кода, а основная реализация расположена в `jvmMain` и использует JVM/Windows зависимости. Его нельзя без проверки подключить как общую Android-библиотеку. Сначала сохраняем его как Windows реализацию, затем переносим безопасные для обеих платформ файлы в прямой общий source directory.

## Предварительная целевая структура

Предварительная структура единого Gradle-репозитория:

```text
Notio/
  shared/src/             одинаковые Kotlin-файлы, напрямую включённые в оба приложения
  app/                    Android оболочка, UI, манифест и Android интеграции
  desktopApp/             Windows оболочка, UI, Windows интеграции и дистрибутивы
  windowsShared/          временный Windows-only код из нынешнего JVM-модуля shared
  docs/                   общие продуктовые и архитектурные договорённости
```

`windowsShared/` — переходное сохранение текущей Windows реализации; код можно переносить из него в `shared/src/` после проверки зависимостей, API и поведения на Android. Совпадение импортов Kotlin/Compose само по себе ещё не доказывает, что файл пригоден для обеих платформ.

## Что развивать совместно

- Модели папок и заметок, правила списков, бюджетов, расписаний и остальных типов заметок.
- Валидацию, сортировку, вычисления, обработку комментариев и операции предметной области.
- Смысл резервных копий, импорта и экспорта; версионирование и миграции их форматов.
- Контракты LAN-синхронизации, сериализацию и правила разрешения конфликтов.
- Форматно-независимые тестовые данные и проверки совместимости.
- Общие тексты и переводческие исходники, если единый источник не ухудшает генерацию ресурсов платформ.

## Что оставить платформенным

- Android Activity, разрешения, Room/Android SQLite, Keystore, CameraX, Media3, уведомления и системную навигацию.
- Windows окно, трей, запуск вместе с системой, DPAPI, файловые пути, SQLite JDBC, обнаружение устройств и вызовы Windows API.
- Элементы интерфейса, зависящие от размеров окна, мыши, клавиатуры, сенсорного ввода и соглашений конкретной платформы.
- APK, подпись Android, EXE/MSI WiX-настройки, portable ZIP и установочные действия.

Compose UI можно переносить в общую папку только после проверки поведения на обеих платформах. Сам факт использования Compose в обоих клиентах не означает, что любой экран следует переносить без адаптации.

## Правила совместимости

1. Одинаковые действия пользователя должны сохранять одинаковый смысл данных на обеих платформах.
2. Схема локальной БД может различаться, если общий экспорт и синхронизация остаются совместимы.
3. Изменения резервной копии или протокола синхронизации сопровождаются версией, миграцией/совместимостью и проверкой обоих клиентов.
4. Существующие идентификаторы приложения, данные пользователей, ключи и опубликованные форматы нельзя менять случайно при переносе.
5. Для каждого переносимого сценария фиксировать, что реализовано общим кодом, а что адаптировано платформенно.

Изменения Android в такие файлы вносились трёхсторонним слиянием (`windows/AGENT.md` D78); перенос в `shared/src` — следующий шаг.
