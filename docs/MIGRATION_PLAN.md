# План объединения Notio-Android и Notio-Windows

Эталонные каталоги `D:\Notio-Android`, `D:\Notio-Windows` и `D:\FitEasy` остаются без изменений. Работы по объединению выполняются только в `D:\Notio`.

## Этап 1. Зафиксировать исходное состояние

- Сохранить версии и ревизии обоих Notio, Gradle/JDK/SDK, идентификаторы приложений, версии схем, резервных копий и протокола синхронизации.
- Составить перечень функций, моделей и форматов в Android и Windows; отметить совпадающее, отличающееся и пока отсутствующее.
- Отдельно зафиксировать версии библиотек и платформенные требования.
- Проверить лицензионные файлы и условия переноса. У Windows-проекта и Android-проекта сейчас не одинаково оформлена лицензия; решение должно предшествовать публикации объединённого исходника.

**Выполнено при импорте:** исходники помещены в `android/` и `windows/`; истории исходных веток связаны с общей веткой через локальные import-коммиты. Существовавшая на момент импорта незакоммиченная правка `Notio-Windows/AGENT.md` также сохранена.

## Этап 2. Подготовить единый Gradle-корень

- Создать один корневой Gradle-проект по образцу FitEasy с Android `:app`, Windows `:desktopApp`, прямым общим source directory и единым каталогом версий.
- Сохранить текущий Windows `shared` модуль временно как Windows-only модуль и перенести его код в общий source directory только после аудита API и зависимостей.
- Сохранить их application ID, package name, схемы данных и настройки подписи.
- Согласовать плагины и версии Kotlin, Compose, AGP и Gradle так, чтобы одной сборкой строились все платформы.
- Один файл версий `version.properties`; у Android и Windows в нём свои линии (`android.*`, `windows.*`), пока функции не сравняются (решение владельца, 2026-10-04).
- Общие версии плагинов и библиотек — в корневом `gradle/libs.versions.toml`. Вложенные Gradle-корни (`gradlew`, `gradle/`, `settings.gradle.kts`, корневые `build.gradle.kts`, `gradle.properties`) в `android/` и `windows/` удалены 2026-10-04: они больше не собирались; их содержимое есть в истории Git.

## Этап 3. Убирать дублирование по слоям

Переносить небольшими функциональными срезами:

1. Чистые модели, перечисления, вычисления и валидацию переносить в `shared/src`.
2. Общие сериализуемые контракты и обработку форматов переносить туда же, если зависимости совместимы с Android и JVM.
3. Хранилища и системные адаптеры оставить в Android app и Windows desktop либо за общими интерфейсами с отдельными платформенными реализациями.
4. Экраны и ввод — отдельно оценивать на обеих платформах; переносить UI-компоненты только с проверенной адаптацией.
5. Тестовые наборы использовать для контроля одинакового поведения общих правил и совместимости данных.

После каждого среза сверять результат с эталонами, не изменяя их. Не заменять рабочую платформенную реализацию общим кодом, пока Android и Windows не способны выполнить тот же пользовательский сценарий.

## Этап 4. Перенести ресурсы и документацию

- Сделать единый источник переводов и автоматическую генерацию Android/Desktop ресурсов либо сохранить синхронизацию, но направить её на ресурсы внутри монорепозитория.
- Перенести и связать функциональные описания, инструкции разработки, заметки о безопасности, решения и историю изменений.
- Сохранить платформенные руководства отдельными документами и указать, где поведение намеренно различается.
- Обновить пути сборочных скриптов, не обращаясь к соседним `D:\Notio-Android` или `D:\Notio-Windows`.

## Этап 5. Общая поставка

Корневая задача `:packageDelivery` собирает Android debug/release APK и Windows EXE/MSI/portable ZIP из одного checkout и общей версии.

## Готовность к завершению объединения

- Все пять требуемых артефактов строятся из одного checkout и одной версии.
- Android и Windows проходят общий набор правил и совместимостных проверок.
- Импорт существующих резервных копий и LAN-синхронизация совместимы с выпущенными эталонными версиями.
- Настройки подписи и машинные пути остаются локальными и отсутствуют в Git.
- Инструкции больше не требуют соседних каталогов как исходников сборки.
- Решение о лицензии, истории Git и переносе пользовательских схем/идентификаторов документировано.
